INTRODUCTION                                                *rules-introduction*

rules.nvim reads a set of rules you point it at, runs whichever of them can
be checked mechanically against a repo, and reports the rest as a worklist.
It ships with no bundled rules of its own — see the README's "Why no bundled
rules".

==============================================================================
SETUP                                                              *rules-setup*
>lua
    require("rules").setup({
      rulesets = { "~/path/to/your/checklists" },
    })
<
`rulesets` is a list of files or directories; every `.md` file reachable from
each entry is scanned for fenced ```rule blocks. Each entry is expanded
(`~`, `$VAR`/`${VAR}`, `%VAR%`) before it is checked, so the `~/...` form
above works as written; a path that still resolves to neither a directory
nor a readable `.md` file is a load error, notified rather than silently
loading zero rules.

`lua_predicates` (boolean, default `true`) decides whether `lua_predicate`
checks may run. A rule block body is always evaluated in an empty environment,
but a predicate is arbitrary Lua that runs later; set `lua_predicates = false`
to run a ruleset you did not write, and each predicate then reports `error`
("predicate not trusted") instead of running. A predicate also runs only in a
ruleset you named yourself (setup({ rulesets }), your vault from setup() or
$RULES_VAULT, a command line): a ruleset that a project `.rules.json` names, or
a vault that file names, reports `error` ("not run: ruleset is not trusted")
unless its folder is in `trust` (setup({ trust = { "~/rules" } }); headless:
--trust=<dir>, $RULES_TRUST). See docs/CONFIG.md and docs/RULESET-FORMAT.md.

==============================================================================
SETTINGS FILES                                                     *rules-config*

Besides setup(), `rulesets`, `gates` and an `agent` block can come from a
`.rules.json` in the root being checked (the `path` of :Rules check/gate, else
the working directory) and from the `.rules.json` of a vault. Highest first:
a headless call (--ruleset, --gate, $RULES_RULESETS, $RULES_GATES), setup(),
the project file, the vault file, the defaults. `rulesets` is taken whole from
the highest place that names it; `gates` is merged by gate name; `agent` field
by field. `lua_predicates` and `trust` are setup() options only. In a file, `[]`
and `{}` are told apart: a list where an object is meant (or the reverse) is an
error, not "empty".
>json
    {
      "rulesets": ["docs/rules", "@vault/lua"],
      "gates": { "release": ["REL"] },
      "agent": { "batch_size": 8, "scopes": { "LUA": { "include": ["lua/**"] } } },
      "vault": "../rules-vault"
    }
<
Paths are relative to the file that holds them. A file that is there but
cannot be used (not JSON, not an object, a value of the wrong shape, over
1 MiB) is an error naming the file and the key, never "no settings"; :Rules
check and :Rules gate stop with it. An unknown key warns, with the nearest
known key as a hint. An absolute path in a project file warns (a path of this
machine in a repository), and so do an entry outside the project folder and a
`vault` key (their rulesets are not trusted, see |rules-config|). A missing file
is not an error. See docs/CONFIG.md.

==============================================================================
VAULT                                                              *rules-vault*

The rules-vault is a folder (a repository of its own) with your rulesets under
`rulesets/<name>/`. It is found from `setup({ vault = "~/rules-vault" })`,
then `$RULES_VAULT`, then `vault` in the project's `.rules.json`; a path is
never guessed, and no vault is not an error. With a vault, every folder under
`rulesets/` is loaded (the vault's own `.rules.json` may narrow or extend
that), and `rulesets` entries of setup() or a project file may name one with
`@vault/<name>` instead of a path. The name in a document's `source` stays the
folder name (`lua`, `native`).
>lua
    local vault = require("rules.vault")
    vault.root()      -- path, or nil and a message (also for a broken vault file)
    vault.source()    -- "call" | "setup" | "env" | "project" | nil, then its problem
    vault.rulesets()  -- the folders the vault offers; {} and the problem if broken
<
:checkhealth rules shows the vault, where it came from, its rulesets, and
whether it is a clean git repository (read-only, no network).

|:RulesVault| opens, copies, links, searches and shows what is in the vault,
and makes one (`:RulesVault create <dir>`).

COMMANDS                                                        *rules-commands*

                                                                  *:Rules_check*
:Rules check [{path}]
    Runs every rule whose ID prefix matches the required |--family| flag
    against {path} (default: the current working directory). Findings go to
    the quickfix list; a readable report opens in a tab, reusing a still-
    open report window instead of piling up a new one on every run. With
    --format=json, prints JSON instead and skips the quickfix list/buffer;
    never quits Neovim, so it is safe to run interactively. For a headless
    CI run with a real exit code, call
    `require("rules").check_family_json(family, path)` directly — see
    docs/BINDINGS.md in the plugin's repository for the recipe.

    --family={PREFIX}     required, e.g. --family=DEP
    --format={FORMAT}     optional, only "json" is recognized

                                                                   *:Rules_gate*
:Rules gate {name} [{path}]
    Runs every family configured for gate {name} (see |rules-gates|) as one
    combined report. --diff={ref} narrows findings to files changed since
    that git ref (tracked + untracked); a rule left with no findings inside
    the diff reports "pass". --format=json behaves like :Rules check's.

    --diff={REF}          optional, e.g. --diff=main
    --format={FORMAT}     optional, only "json" is recognized

                                                                   *:Rules_show*
:Rules show {id}
    Jumps straight to one rule's source location by its exact id (e.g.
    `:Rules show DEP-06`), without running a family check. Errors, rather
    than silently doing nothing, if no loaded rule has that id.

                                                                  *:Rules_stats*
:Rules stats
    A structural overview of every loaded rule: total count, and per-family
    totals split into automated (has a `check`) vs. manual, plus a severity
    breakdown. No check runs — this is catalog metadata, not a pass/fail
    report; opens in a readable buffer, or prints JSON with --format=json.

    --format={FORMAT}     optional, only "json" is recognized

                                                                *:Rules_catalog*
:Rules catalog [{path}]
    For a ruleset in the one-file-per-rule form (see |rules-ruleset-format|):
    builds the reading documents from their layouts. {path} is a ruleset
    folder (default: every folder in `rulesets`). A document is written only
    when its content changed. With --check nothing is written and every
    document that is out of date is reported; for CI use
    `nvim --headless -u NONE -l scripts/ruleset.lua catalog --check {folder}`
    (exit code 1 when one is). Rules that are in no layout are named.

    --check               optional, only report

                                                                    *:Rules_new*
:Rules new [{family} [{title}...]] [severity={level}] [text={text}]
                                  [ruleset={name}] [{place}] [--yes] [--dry]
    Makes a rule in a ruleset of the one-file-per-rule form, at the next
    free id of {family}. With the family, a title and severity= the rule
    is made, placed and opened. With less, a Markdown form opens, filled in
    with what was given (|rules-form|). The command checks nothing of a rule
    itself: it hands one operation of `rules-ops/1` to the engine and tells
    the answer. --dry checks everything and writes nothing.

    In a rules-vault that lies behind its upstream (what the last `git fetch`
    knows) the rule is made and a warning follows: pull before you make a
    rule, or another machine may make the same id. The engine never pulls,
    fetches or commits.

    {family} is 1 to 12 uppercase letters A-Z (DEP), or a family the
    ruleset has already, spelled exactly as there (`Dep-01` goes on with
    `Dep-02`): `Fix` or `dep` is refused, so a mistyped title does not make
    a family. A family that no
    rule has yet is asked about before the first rule is made (--yes skips
    the question).

    A `key=` word may stand before the family (it takes one word); the
    family is the first word that is no known `key=`. A value is taken
    from the line as typed (runs of blanks and backslashes stay). A word
    with two dashes is a flag, also inside a value. A bare `--` ends the
    flags only right behind the first word (the family, the id) or in
    front of a word that starts with a dash, so `text=run with -- --dry
    now` is the text `run with --dry now` (the `--` is not part of it);
    anywhere else it is text, kept: `text=Use this -- not that --dry` is a
    dry run of `Use this -- not that`.

    {place} is one of
    --to={file}#{section}   layout (its `output` path) and heading text; write
                            a blank in the heading as `\ `; {file} alone is
                            the top of the layout
    --after={id}            right after that rule, in the layout that holds it
    --before={id}           right before that rule
    --first                 with --to: the start of the section, not its end
                            (a section with no rule yet: behind its intro)

                                                                    *:Rules_set*
:Rules set {id} {key}={value}... [--dry]
    Changes parts of a rule's file; every line it was not asked to change
    stays byte for byte (a check= leaves the agent of the block as it is, and
    the other way round). Keys: severity, title, text, check, agent. A value may hold
    spaces (a word that is no known `key=` goes on with the value before
    it). check= and agent= take a JSON object, or nothing to remove the key.
    An open buffer of the file is reloaded; one with unsaved changes is
    reported as a conflict and left as it is. --dry shows the change as a
    diff.

                                                                 *:Rules_retire*
:Rules retire {id} [--by={id}] [reason={text}] [--yes] [--dry]
    Moves the rule's file to `_retired/` and out of every layout; the id
    stays taken. Asks first (--yes skips the question; a session without a
    screen needs it). The engine is asked with a dry run before the
    question, so a rule that is not there is told without one. --by names
    the rule that takes its place.

                                                                   *:Rules_move*
:Rules move {id} {place} [--dry]
    Moves the rule's `{{rule ID}}` line within its layout or into another;
    the rule's own file is not touched. {place} as in |:Rules_new|, one is
    required.

                                                                   *:Rules_list*
:Rules list [--family={PREFIX}] [--severity={level}] [--format=json]
    Puts the rules in the quickfix list, each at its source line. With
    --format=json prints the `rules.list` document of the machine contract.

                                                                   *:RulesVault*
:RulesVault {verb} [{ruleset}|{id}|{family}] [{part}]
    Navigates to where the rules are, like :TasksVault does for tasks. It
    reads and points; it writes nothing but the scaffold of `create`. A rule
    is made by |:Rules_new|, so there is no `new` and no `paste`. The vault is
    found as |rules-vault| says; without one every verb but `create` says so
    once. A word is read as a ruleset of the vault (its folder name), a part,
    a rule id or a family, in that order; `<Tab>` offers all of them. {part}
    is one of
    rules                   the rule files, `_rules/` (default)
    layouts                 `_layouts/`
    catalogs                the generated reading documents
    all                     the ruleset folder
    Without a word the ruleset is the one of the current buffer, the only
    one, or a pick. A rule id or a family has no part.

    open                    a rule file (a retired rule too), the folder of a
                            family, or a part of a ruleset
    clipboard               the path to the + register; --rel relative to the
                            current file; --link as `[DEP-06](path)`
    link                    a Markdown link at the cursor, relative to the
                            current file
    find, grep              a pickers.nvim picker in the ruleset (for an id:
                            searching for the id), the family or the part
    tree                    the ruleset as a tree, family then rules, counts
                            per family, retired rules marked `[retired]`
    cdx                     a prompt for an agent session to the + register
    create [{dir}] [{name}] a vault: README.md, .rules.json,
                            .gitattributes, .gitignore, the CI workflow and a
                            first ruleset (default name `default`). Lists
                            first what happens and the step that is left to
                            you (set `vault` in setup() or $RULES_VAULT: it
                            is marked REQUIRED), then asks. A file that is
                            there is never overwritten; no remote is ever
                            added.

    --git                   create: run `git init` (only then)
    --yes                   create: skip the question (needed without a screen)
    --force                 create: make a vault although one is in use
    --rel                   clipboard, cdx: relative to the current file
    --link                  clipboard: a Markdown link

                                                                    *rules-form*
THE FORM OF :Rules new ~

A Markdown buffer (`rules://rule-new`) with the lines Family, Title, an
optional Ruleset and Place, a list of severities and, below `## text`, the
prose of the rule. Family, Title and one severity are required.

    <Space>, <CR>   tick or untick the severity under the cursor (one tick)
    <C-s>           check the form (what is missing is listed at the top as
                    `!` lines), ask the engine with a dry run, show what
                    would be made and ask; only "Create the rule" writes
    q, <C-q>        cancel; asks first when something was typed
    g?              help

==============================================================================
GATES                                                             *rules-gates*

A gate is a named bundle of rule families, run together as one report — the
one place in this plugin that checks more than one family at once. No gates
are bundled; define them in `setup()`: >lua
    require("rules").setup({
      gates = {
        release = { "REL" },
        review = { "ERR", "LUA", "PRIN" },
      },
    })
<
See docs/BINDINGS.md in the plugin's repository for the `--diff` scoping
semantics in detail. A configured family that matches zero loaded rules
(a typo, or a family not yet migrated to fenced `rule` blocks) warns rather
than silently running a smaller gate than configured.

==============================================================================
WAIVERS                                                          *rules-waivers*

A `.rules-waivers.json` at the checked root records consciously accepted
findings so a re-run doesn't keep flagging them: >json
    { "DEP-04": "legacy call site, ticket JIRA-123 tracks the actual fix" }
<
A waived rule that would otherwise fail or error reports as "waived"
instead of "fail" — visible in the buffer report with its reason, excluded
from the quickfix worklist, and never counted by `check_family_json`'s exit
code. See docs/BINDINGS.md in the plugin's repository for detail.

`:checkhealth rules` cross-checks the current working directory's waivers
against every loaded rule and warns about an orphaned entry — a waiver
whose rule id was retired or mistyped, which would otherwise sit silently
protecting nothing.

==============================================================================
RULESET FORMAT                                            *rules-ruleset-format*

See docs/RULESET-FORMAT.md in the plugin's repository for the full format —
this is the reference for a Lua project's own `:h` request, not a duplicate
of that document's detail.

A rule is a Markdown section with a fenced ```rule code block:
>markdown
    ### `DEP-06` — `vim.tbl_flatten()` is deprecated

    ```rule
    id = "DEP-06",
    severity = "recommended",
    check = { type = "grep", pattern = "vim%.tbl_flatten%(" },
    ```
<
`check` is optional. A rule without one is never given an automatic
pass/fail — it appears as a worklist entry instead.

A rule can also be a file of its own: a frontmatter with `id` and `severity`
(and optionally `family`), then the rule as it reads; a ```rule block only
when the rule has a `check` or an `agent`, and then without the two identity
lines. The reading documents are generated from layouts (|:Rules_catalog|), and
`scripts/ruleset.lua migrate` converts a ruleset of documents into that form.
Both forms load side by side. See docs/RULESET-FORMAT.md.
